# シナリオテンプレート

新しいユースケースシナリオを追加するときは、このページをコピーしてください。すべてのシナリオは同じ 7 つのセクションで構成され、読者がシナリオを一目で比較できるようにします。

各セクションは短く具体的に保ち、[`.github/workflows/`](../../.github/workflows) 配下の **動作する** ワークフローにリンクしてください。実際にコンパイルできるワークフローを紐づけるまで、シナリオは完成とはみなしません。

---

## 1. 背景・課題

チームの状況と課題を記述します。誰が、どのくらいの頻度で困っているのか、手作業での対応がなぜコスト高または間違いを招きやすいのかを説明します。

## 2. 自動化ゴール

1〜2 文で記述します。ワークフローが何を達成すべきか、そしてそれが機能したとどう判断できるか（観測可能な成果）を示します。

## 3. 設計: トリガー・permissions・safe-outputs

| 項目 | 選択 | 理由 |
| --- | --- | --- |
| トリガー (`on:`) | … | ワークフローを実行すべきタイミング |
| 権限 (permissions) | … | 最小権限 |
| safe-outputs | … | 唯一の書き込み経路 |
| エンジン | `copilot` | リポジトリの既定 |

## 4. 動作ワークフローへのリンク

ワークフローの Markdown とコンパイル済みの `*.lock.yml` にリンクし、実行方法を示します。

## 5. Human-in-the-Loop（承認点）

人間はどこで制御を保つのか。承認・意思決定のポイントと、エージェントに明示的に **許可しない** ことを特定します。

## 6. コスト・セキュリティ注意

トリガーの頻度とコストへの影響、権限のスコープ、フォークや信頼できない入力の扱い、関係するシークレットについて記述します。[実行アーキテクチャ](../concepts/execution-architecture.ja.md)を参照してください。

## 7. 発展

シナリオを発展させるアイデア: より充実したプロンプト、追加の safe-outputs、コマンドトリガー、他のワークフローとの組み合わせなど。
