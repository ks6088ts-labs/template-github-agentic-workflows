# PR レビュー補助

> ペルソナ: ① ソフトウェア開発者 · [シナリオテンプレート](../TEMPLATE.ja.md)に従います。

## 1. 背景・課題

すべてのプルリクエストには一次レビューが必要です。主張どおりの動作をするか、明らかなバグやセキュリティ問題はないか、テストされているか、チームの規約に従っているか。多忙なリポジトリでは、この一次レビューがボトルネックになります。レビュアーは作業を中断され、PR が注目を待つ間に小さな問題が見過ごされてしまいます。

## 2. 自動化ゴール

プルリクエストがオープンまたは更新されたとき、エージェントが変更を要約し、最も重要な指摘を列挙した 1 件の構造化されたレビューコメントを投稿します。このコメントは人間のレビュアーの助走になりますが、エージェント自身がマージや承認を行うことはありません。

## 3. 設計: トリガー・permissions・safe-outputs

| 項目 | 選択 | 理由 |
| --- | --- | --- |
| トリガー (`on:`) | `pull_request`（`opened`、`synchronize`、`reopened`） | 新規・更新された PR に自動で反応 |
| 権限 (permissions) | `contents: read`、`pull-requests: read` | 最小権限 — エージェントは差分を読むだけ |
| safe-outputs | `add-comment`（`max: 1`） | 唯一のサニタイズ済み書き込み経路 — 1 実行につき 1 コメント |
| エンジン | `copilot` | リポジトリの既定 |

エージェントのジョブは読み取り専用で実行されます。コメントはエージェントの完了 **後** に、権限を絞った別スコープの safe-outputs ジョブが書き込みます。エージェント自身は書き込み権限を持ちません。[実行アーキテクチャ](../../concepts/execution-architecture.ja.md)を参照してください。

## 4. 動作ワークフロー

- ワークフロー: [`.github/workflows/pr-review-helper.md`](../../../.github/workflows/pr-review-helper.md)
- コンパイル済み: [`.github/workflows/pr-review-helper.lock.yml`](../../../.github/workflows/pr-review-helper.lock.yml)

編集後はコンパイルと検証を行います:

```bash
make compile
make ci-test
```

試すには、リポジトリでプルリクエストをオープンします。事前に `COPILOT_GITHUB_TOKEN` シークレットを設定しておく必要があります — [はじめに](../../tutorials/01_getting-started.ja.md)を参照してください。

## 5. Human-in-the-Loop（承認点）

承認点はプルリクエストのレビューそのものです。エージェントは **コメントするだけ** で、人間が指摘を読んで対応を判断します。設定上、エージェントは承認・正式な変更要求・マージ・ファイルの変更を行えません。これにより、一次レビューの立ち上げコストを取り除きつつ、人間を意思決定ループの中心にしっかりと留めます。

## 6. コスト・セキュリティ注意

- **コスト**: `pull_request` はオープン中の PR への push ごとに実行されます。多忙なリポジトリでは、トリガーを絞る（例: `paths:` フィルター）か、オンデマンドのコマンドトリガー（`/review`）に切り替えます。[実行アーキテクチャ → イベント駆動のコスト](../../concepts/execution-architecture.ja.md)を参照してください。
- **最小権限**: 読み取り専用の権限で、副作用は 1 件のコメントのみです。
- **信頼できない入力**: PR のタイトル・説明・差分は信頼できないコンテンツです。gh-aw はイベントテキストをサニタイズし、パブリックリポジトリでは integrity filtering を自動的に適用します。権限は読み取り専用に保ち、シークレットを出力しないでください。

## 7. 発展

- `create-pull-request-review-comment` safe-output でインラインのレビューコメントを追加する。
- `/review` コマンドの背後にワークフローを配置し、push ごとではなくオンデマンドで実行する。
- チームのスタイルガイドやレビューチェックリストに合わせてプロンプトを調整する。
- Issue トリアージやリリースノートのワークフローと組み合わせ、より充実した開発ループにする。
