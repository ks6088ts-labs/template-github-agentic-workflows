# ワークフローのフォーマットとコンパイルパイプライン

gh-aw のワークフローがどう定義され、コンパイラが何をし、何を生成するか。公式の
[Compilation Process](https://github.github.com/gh-aw/reference/compilation-process/)、
[Frontmatter](https://github.github.com/gh-aw/reference/frontmatter/)、
[Workflow Structure](https://github.github.com/gh-aw/reference/workflow-structure/)
を要約したものです（[出典](#出典)参照）。

## 2 部構成

各ワークフローファイルは 2 部から成ります:

1. **YAML フロントマター**（`---` で囲む）: トリガー、権限、エンジン、ツール、safe-outputs など
2. **マークダウン本文**: エージェントへの自然言語指示

```markdown
---
on:
  issues:
    types: [opened]
tools:
  github:
    toolsets: [issues]
---
# Workflow description
Read issue #${{ github.event.issue.number }} and comment with useful links.
```

メイン本文の後ろに、インラインのサブエージェント定義を任意で追加できます。

## フォーマットの定義はどこにあるか

人間向けの仕様は Frontmatter / Workflow Structure リファレンスです。**真の source of truth**
は [`github/gh-aw`](https://github.com/github/gh-aw) リポジトリ内の機械可読な
**ワークフロー JSON Schema**（`main_workflow_schema.json`）で、コンパイラはフロントマターを
これに照らして検証します。フロントマターのフィールドを追加するには schema を更新して再ビルドします。

> schema の**ファイル名**は確認済みですが、正確なパス（`pkg/parser/` 配下と見られる）は
> バージョンにより異なる可能性があります。ファイル名でリポジトリ内検索するのが確実です。

### 主なフロントマターフィールド

| フィールド | 用途 |
| --- | --- |
| `on:` | トリガー（標準の GitHub Actions トリガー＋ `reaction`、`stop-after`、`roles`、`skip-if-match` など） |
| `permissions:` | エージェントの GitHub 読み取り権限 |
| `engine:` | 本文を解釈する AI エンジン（`copilot`、`claude`、`codex` など） |
| `tools:` | エージェントに与える GitHub API・bash・ブラウザ・MCP ツール |
| `mcp-servers:` | 外部サービス連携のための MCP サーバ定義 |
| `network:` | ネットワーク egress 許可（エコシステム識別子／ドメイン） |
| `safe-outputs:` | サニタイズされた書き込み操作（Issue 作成・コメントなど） |
| `imports:` | 共有コンポーネント（tools/steps/MCP/prompt）の再利用 |
| `pre-steps:` / `steps:` / `post-steps:` / `jobs:` | 決定論的なカスタムステップ・ジョブ |
| `secrets:` | ワークフローに渡す秘密値（`${{ secrets.* }}` で参照） |
| `env:` | ワークフローレベル環境変数 — **秘密は書かない**（下記参照） |
| `runtimes:` | 言語ランタイムのバージョン上書き |
| `strict:` | 厳格モード（既定 `true`。カスタムドメイン許可には `strict: false` が必要） |

> **ワークフローレベルの `env:` に `${{ secrets.* }}` を書かないこと。** env はエージェント
> コンテナに直接渡り、秘密がモデルから見えてしまいます。**strict モードではコンパイルエラー**
> です。秘密は safe-output/MCP または決定論ステップ経由で渡してください
> （[外部連携](external-integrations.ja.md)参照）。

## コンパイル: 決定論的・LLM 不使用

`gh aw compile` はマークダウンワークフローを完全な GitHub Actions `.lock.yml` に変換し、
フロントマターを埋め込み、本文は**実行時にロード**するよう構成します。コンパイルは
**決定論的で LLM を使いません** — エンジンが動くのは実行時の agent ジョブだけです。

### 5 つのコンパイルフェーズ

| # | フェーズ | 内容 |
| --- | --- | --- |
| 1 | 解析と検証 | frontmatter 抽出、schema 検証、式の安全性チェック（許可リストのみ）、imports 解決（BFS・循環検出） |
| 2 | ジョブ構築 | `pre-activation` / `activation` / `agent` / `safe-outputs` / safe-jobs / カスタムジョブを構築 |
| 3 | 依存解決 | 依存検証、循環検出、トポロジカル順序、Mermaid グラフ |
| 4 | アクションピン留め | 全アクションを commit SHA に固定（解決順: キャッシュ → GitHub API → 埋め込みピン） |
| 5 | YAML 生成 | ヘッダメタデータ、Mermaid グラフ、ジョブ（アルファベット順）、埋め込みプロンプトを組み立て |

### `.lock.yml` のヘッダ

各 `.lock.yml` は機械可読なメタデータ行で始まり、外部依存の人間可読マニフェストが続きます:

```yaml
# gh-aw-metadata: {"schema_version":"v3","frontmatter_hash":"…","strict":true,"agent_id":"copilot"}
# This file was automatically generated by gh-aw. DO NOT EDIT.
# Secrets used:
#   - COPILOT_GITHUB_TOKEN
#   - GITHUB_TOKEN
# Custom actions used:
#   - actions/checkout@de0fac2… # v6.0.2
```

`Secrets used` / `Custom actions used` は、`secrets.*` 参照と外部 `uses:` 依存（ローカル
`./` 参照を除く）をソート・重複排除して列挙します。

### 「オフライン」の条件

フェーズ 4 は `tag → SHA` の解決に GitHub API を必要とします — ただし、コミット済みのピン
キャッシュ `.github/aw/actions-lock.json` に SHA があれば、コンパイルは完全にオフラインで
再現可能です。キャッシュをコミットしておけば、新規解決が要るのは初回（未キャッシュ）だけです。

### 再コンパイルが必要なとき

- **不要** — マークダウン**本文**のみの編集（実行時ロード。GitHub.com 上で直接編集しても可）。
- **必要** — **フロントマター**の変更時。

### 主要コマンド

| コマンド | 説明 |
| --- | --- |
| `gh aw compile` | `.github/workflows/` の全ワークフローをコンパイル |
| `gh aw compile <name>` | 特定ワークフローのみ |
| `gh aw compile --strict` | 厳格モード検証を強制 |
| `gh aw compile --no-emit` | 検証のみ（lock ファイルを生成しない） |
| `gh aw compile --purge` | 孤立した `.lock.yml` を削除 |
| `gh aw validate [name]` | コンパイル＋全 linter（ファイル出力なし） |
| `gh aw upgrade` | エージェントファイルとワークフローの更新（codemod・アクションピン更新・再コンパイル） |

> アクションピンは `gh aw compile` / `gh aw upgrade` が更新します（専用コマンドはありません）。
> `gh aw update` は各ワークフローをソースリポジトリから更新します。

## `.github/aw/` ディレクトリ

`.github/aw/` は、**リポジトリにコミットする**コンパイル時成果物の置き場で、中心は
`actions-lock.json` です。`.lock.yml` 同様に自動生成物（手編集しない）でありながら、
**バージョン管理で共有**します。

### `actions-lock.json`

- **何か**: `action@version → commit SHA` の解決結果を記録したキャッシュ／ロック。
- **なぜ**: フェーズ 4 で全アクションを不変の SHA に固定します（tag は動くが SHA は不変）—
  サプライチェーン対策。解決順は キャッシュ → GitHub API → 埋め込みピン。
- **なぜコミットするか**: (1) 再現性（誰がコンパイルしても同じ SHA）、(2) 制限トークン環境
  （例: Copilot コーディングエージェント）でも動く、(3) 全 contributor・ツールが同一ピンを共有。

| 場面 | やること |
| --- | --- |
| 新規セットアップ | 自動生成される → そのままコミット |
| ピンを更新 | `gh aw upgrade` を実行（手編集しない） |
| ピンを全解決し直す | 削除して、権限のあるトークンで再コンパイル |
| 制限トークン環境 | 事前に広い権限のトークンで生成・コミット |
| マージコンフリクト | 手で直さず再コンパイルで再生成 |
| Dependabot の `github/gh-aw-actions` bump PR | merge しない — `gh aw compile` がピンを一元管理し `dependabot.yml` に無視ルールを自動挿入 |

### 実行時の一時ファイルとの違い

コミットするロック（`.github/aw/`）と、実行時の一時成果物（`/tmp/gh-aw/` 配下の
`agent_output.json`、`prompt.txt`、`agent_usage.json`、firewall ログ …）は別物です。
後者は `gh aw logs <run-id>` で参照します。

## セキュリティ: コンパイル後のジョブ分離

コンパイル済みワークフローは、エージェント後段を独立したジョブに分けます（GitHub Actions の
権限はジョブ単位で不変のため統合できません）:

| ジョブ | 主な権限 | 役割 |
| --- | --- | --- |
| `detection` | `contents: read` | エージェント出力を AI で脅威スキャン（書き込み権限なし） |
| `safe_outputs` | `contents` / `issues` / `pull-requests: write` | GitHub API 書き込みを実行 |
| `conclusion` | `issues` / `pull-requests` / `discussions: write` | 結果集約・失敗処理・サマリ |

`safe_outputs` は `needs.detection.outputs.success == 'true'` を条件とし、検知失敗時は書き込み
ジョブが起動しません。この **Plan-Level Trust** が、読み取り専用の AI 推論と書き込み操作を
分離します。[実行アーキテクチャ](execution-architecture.ja.md)参照。
