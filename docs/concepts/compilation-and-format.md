# Workflow format and the compile pipeline

How a gh-aw workflow is defined, what the compiler does, and what it produces. This
distills the official [Compilation Process](https://github.github.com/gh-aw/reference/compilation-process/),
[Frontmatter](https://github.github.com/gh-aw/reference/frontmatter/), and
[Workflow Structure](https://github.github.com/gh-aw/reference/workflow-structure/)
references; see [Sources](#sources).

## Two-part structure

Every workflow file has two parts:

1. **YAML frontmatter** (between `---`): triggers, permissions, engine, tools, safe-outputs, …
2. **Markdown body**: natural-language instructions for the agent.

```markdown
---
on:
  issues:
    types: [opened]
tools:
  github:
    toolsets: [issues]
---
# Workflow description
Read issue #${{ github.event.issue.number }} and comment with useful links.
```

An optional inline sub-agent definition may follow the main body.

## Where the format is defined

The human-readable spec is the Frontmatter and Workflow Structure references. The
**source of truth** is the machine-readable **workflow JSON Schema** (`main_workflow_schema.json`)
in the [`github/gh-aw`](https://github.com/github/gh-aw) repository — the compiler validates
frontmatter against it. Adding a frontmatter field means updating the schema and rebuilding.

> The schema **file name** is confirmed; its exact path (believed to be under `pkg/parser/`)
> can vary by version — search the repo by file name to locate it.

### Key frontmatter fields

| Field | Purpose |
| --- | --- |
| `on:` | Triggers (standard GitHub Actions triggers plus `reaction`, `stop-after`, `roles`, `skip-if-match`, …) |
| `permissions:` | Read-only GitHub scopes for the agent |
| `engine:` | AI engine that interprets the body (`copilot`, `claude`, `codex`, …) |
| `tools:` | GitHub API, bash, browser, and MCP tools granted to the agent |
| `mcp-servers:` | MCP server definitions for external services |
| `network:` | Network egress allowlist (ecosystem identifiers / domains) |
| `safe-outputs:` | Sanitized write operations (create issue, comment, …) |
| `imports:` | Reuse of shared components (tools/steps/MCP/prompt) |
| `pre-steps:` / `steps:` / `post-steps:` / `jobs:` | Deterministic custom steps and jobs |
| `secrets:` | Secret values passed to the workflow (referenced as `${{ secrets.* }}`) |
| `env:` | Workflow-level env vars — **never put secrets here** (see below) |
| `runtimes:` | Language runtime version overrides |
| `strict:` | Strict mode (default `true`; custom network domains require `strict: false`) |

> **Do not put `${{ secrets.* }}` in workflow-level `env:`.** `env` is passed straight to the
> agent container, so the model would see the secret. This is a **compile error in strict
> mode**. Pass secrets via a safe-output/MCP or a deterministic step instead — see
> [external integrations](external-integrations.md).

## Compilation: deterministic, no LLM

`gh aw compile` converts the Markdown workflow into a complete GitHub Actions `.lock.yml`,
embedding the frontmatter and loading the body **at runtime**. The compile is
**deterministic and uses no LLM** — the engine only runs at runtime, in the agent job.

### The five compile phases

| # | Phase | What happens |
| --- | --- | --- |
| 1 | Parsing & validation | Extract frontmatter, validate against the schema, check expression safety (allowlisted only), resolve imports (BFS + cycle detection) |
| 2 | Job construction | Build `pre-activation` / `activation` / `agent` / `safe-outputs` / safe-jobs / custom jobs |
| 3 | Dependency resolution | Validate dependencies, detect cycles, topological order, Mermaid graph |
| 4 | Action pinning | Pin every action to a commit SHA (resolution order: cache → GitHub API → embedded pin) |
| 5 | YAML generation | Assemble header metadata, Mermaid graph, jobs (alphabetical), embedded prompt |

### The `.lock.yml` header

Each `.lock.yml` starts with a machine-readable metadata line, then a human-readable
manifest of external dependencies:

```yaml
# gh-aw-metadata: {"schema_version":"v3","frontmatter_hash":"…","strict":true,"agent_id":"copilot"}
# This file was automatically generated by gh-aw. DO NOT EDIT.
# Secrets used:
#   - COPILOT_GITHUB_TOKEN
#   - GITHUB_TOKEN
# Custom actions used:
#   - actions/checkout@de0fac2… # v6.0.2
```

`Secrets used` / `Custom actions used` list the deduplicated `secrets.*` references and
external `uses:` dependencies (excluding local `./` refs).

### Is it "offline"?

Phase 4 needs the GitHub API to resolve `tag → SHA` — **unless** the committed pin cache
`.github/aw/actions-lock.json` already contains the SHA, in which case the compile is fully
offline and reproducible. With the cache committed, new resolutions are only needed the first
time (or for uncached actions).

### When to recompile

- **Not needed** — editing only the Markdown **body** (loaded at runtime); you can even edit
  it directly on GitHub.com.
- **Needed** — any **frontmatter** change.

### Commands

| Command | Description |
| --- | --- |
| `gh aw compile` | Compile all workflows in `.github/workflows/` |
| `gh aw compile <name>` | Compile one workflow |
| `gh aw compile --strict` | Enforce strict-mode validation |
| `gh aw compile --no-emit` | Validate only (no lock files) |
| `gh aw compile --purge` | Delete orphaned `.lock.yml` files |
| `gh aw validate [name]` | Compile + all linters, no emit |
| `gh aw upgrade` | Upgrade agent files and workflows (codemods, action-pin updates, recompile) |

> Action pins are refreshed by `gh aw compile` / `gh aw upgrade`, not by a separate command.
> (`gh aw update` pulls workflow updates from their source repositories.)

## The `.github/aw/` directory

`.github/aw/` holds compile-time artifacts that are **committed** to the repository — chiefly
`actions-lock.json`. Like `.lock.yml`, it is generated (don't hand-edit) but **shared via
version control**.

### `actions-lock.json`

- **What**: a cache/lock recording `action@version → commit SHA` resolutions.
- **Why**: phase 4 pins every action to an immutable SHA (tags can move, SHAs can't) — a
  supply-chain safeguard. Resolution order is cache → GitHub API → embedded pin.
- **Why commit it**: (1) reproducibility — everyone compiles to the same SHA; (2) it works in
  restricted-token environments (e.g. the Copilot coding agent) that can't call the API to
  resolve tags; (3) all contributors and tools share one pin set.

| Situation | Do this |
| --- | --- |
| New setup | It's generated — just commit it |
| Refresh pins | Run `gh aw upgrade` (don't hand-edit) |
| Re-resolve all pins | Delete the file and recompile with a permissioned token |
| Restricted-token env | Pre-generate & commit with a broad token first |
| Merge conflict | Don't hand-fix — regenerate by recompiling |
| Dependabot PR bumping `github/gh-aw-actions` | Don't merge — `gh aw compile` manages pins and auto-adds an ignore rule to `dependabot.yml` |

### Runtime temp files are different

Committed locks (`.github/aw/`) are not the run-time artifacts under `/tmp/gh-aw/`
(`agent_output.json`, `prompt.txt`, `agent_usage.json`, firewall logs, …). Inspect those with
`gh aw logs <run-id>`.

## Security: the compiled job separation

The compiled workflow splits the post-agent stages into independent jobs (GitHub Actions
permissions are per-job and cannot be merged):

| Job | Key permissions | Role |
| --- | --- | --- |
| `detection` | `contents: read` | AI threat-scan of agent output (no write access) |
| `safe_outputs` | `contents` / `issues` / `pull-requests: write` | Perform the GitHub API writes |
| `conclusion` | `issues` / `pull-requests` / `discussions: write` | Aggregate results, handle failures, summary |

`safe_outputs` is gated on `needs.detection.outputs.success == 'true'` — on a failed scan, the
write jobs never start. This **Plan-Level Trust** separates read-only AI inference from write
operations. See [execution architecture](execution-architecture.md).
